# KIS 일일 운용 모니터링

이 스킬은 코드를 수정하지 않는다. 목적은 "지금 운용 중인 시스템이
정상 작동하는가"를 빠르게 확인하는 것이다. 이상이 발견되면 원인을
보고하고, 코드 수정이 필요하면 kis-code-change 스킬로 넘기라고
안내한다.

## 점검 항목 (우선순위 순)

### 1. 토큰/인증 정상 여부
- `token_mock.json`, `token_real.json` 파일의 최종 수정 시각 확인.
  23시간 캐시 주기(kis_api.py)를 벗어나 갱신이 안 됐다면 토큰 만료
  가능성 — `trader.log`에서 401/인증 오류 로그를 찾는다.
- `get_token()`은 발급 전 캐시 파일을 재확인함(커밋 44268d5) —
  trader와 dashboard가 별도 프로세스여도 토큰 발급은 만료 시 1회만
  일어나는 게 정상. 짧은 간격의 반복 발급 로그가 보이면 이상.
- 실전 전환 후(앱키 동일)에는 `_trade`가 `_real` 클라이언트를 공유하므로
  `token_real.json`만 갱신되고 `token_mock.json`이 멈춰 있는 것이 **정상**.
- 모의/실전 전환 직후라면 두 토큰 파일이 삭제됐는지 확인
  (CLAUDE.md: `del token_mock.json & del token_real.json`).

### 2. trader.log 이상 패턴
- 반복되는 예외(특히 KIS API POST 실패 = 주문 실패, kis_api.py는
  POST 재시도가 없으므로 실패하면 그 주문은 그냥 누락됨)를 찾는다.
- `notifier.send_error()` 호출 흔적이 있는지 확인 — 텔레그램 미설정
  시 print로만 남으므로 로그에서 직접 찾아야 할 수 있다.
- 한글이 깨져 보이면 `$env:PYTHONIOENCODING="utf-8"` 없이 실행된
  것 — 내용 자체는 무시하지 말고 인코딩만 다시 맞춰서 재확인한다.

**오탐 방지 — 알려진 정상 패턴 (이슈로 판정하지 말 것):**
- `[DART] 클라이언트 초기화 실패` WARNING은 **두 가지 발현** 모두
  알려진 한계: ① `'module' object is not callable` (OpenDartReader
  패키지의 sys.modules 바꿔치기 구조 + 병렬 import race) ② `WinError 5`
  / `pickle data was truncated` (corp_codes pkl 동시 접근). 프로세스
  시작 후 첫 배치(주로 08:30)에서 3~9건 발생 후 같은 날 16:00 배치에서
  미발생이면 자가치유 — 정상. **같은 프로세스에서 하루 종일 반복되면**
  그때만 구조적 이상으로 판정.
- 모의서버(`openapivts:29443`) `Read timed out` ERROR는 실측 기준
  주 1~2건 수준의 일회성 네트워크 이슈 — 해당 스캔 1사이클만 유실되고
  다음 사이클(60초 후)에 정상 로그가 이어지면 조치 불필요. 판정 기준:
  ① 다음 사이클 복구 여부 ② 타임아웃 시점 보유 종목 유무(보유 중이면
  청산 판단 1회 지연 발생) ③ 과거 로그 grep 빈도(연속·군집 발생이면
  네트워크/서버 구조 문제로 격상).

### 3. 일일손실한도 상태
- `_daily_loss_halted` 플래그가 전일에 켜진 채로 오늘까지 남아있지
  않은지 확인한다. 날짜가 바뀌면 자동 리셋되는 게 정상
  (trader.py `_daily_loss_date` 비교 로직).
- 만약 한도가 발동했다면, `database.py`의 `daily_summary`에서
  실현 손익을 확인하고 INITIAL_CAPITAL × DAILY_LOSS_LIMIT 계산이
  맞는지 검증한다. 단, 미실현 손실은 이 계산에 포함되지 않는다는
  점(알려진 한계, CLAUDE.md 명시)을 감안해서 해석한다.
- **발동 시 정상 동작 판정 기준**: 한도 발동은 "신규 매수만 중단"이며
  보유 종목 청산(_check_exit)은 계속 진행되는 것이 설계다 (trader.py
  scan()에서 청산 루프가 손실한도 체크보다 먼저 실행됨). 발동 이후
  SELL 로그가 있어도 이상이 아니고, 오히려 발동 이후 보유 종목의
  "보유 유지" 로그가 끊겼다면 그게 이상이다. 또한 발동일의 "매수 0건"은
  당연한 결과이므로 매매 활동 점검(5번)에서 별도 원인 조사를 하지 않는다.

### 4. 캐시 갱신 타이밍
- `news_dart_cache.json` — 16:00 `signal_cache.py` 배치가 정상
  실행됐는지 수정 시각으로 확인. 갱신이 안 됐다면 strategy.py의
  캐시 우선 조회가 계속 "미스캔"으로 폴백되어 매 60초 fresh
  HTTP 호출이 재발할 수 있다 (캐싱 도입 효과 무력화).
- `watchlist_cache.json`, `name_cache.json` — 24시간 캐시 만료
  여부 확인.
- `premarket_cache.json`, `premarket_morning.json` — 16:00 후보,
  08:30 재검증 두 단계가 모두 기록됐는지 확인.

### 5. 매매 활동 점검
- 오늘 BUY/SELL이 전혀 없었다면, 비정상이 아닐 수 있다 — 골든크로스
  자체가 종목당 월 1~2회 빈도이므로 하루에 매매가 없는 게 정상일
  때가 많다. 다만 watchlist 전체(최대 200종목)에서 며칠 연속 매매가
  0건이면 RSI/거래량 필터가 과도하게 막고 있는지 의심해본다.
- `trades.db`의 SELL 누적 건수를 확인하고 30건까지 남은 건수를
  보고한다 (PARAMS LOCKED 해제 조건).
- **trades.db price의 시대 구분**: 2026-07-03 이후 거래는 ODNO 체결
  조회로 **실제 체결가** 기록 (커밋 42b7a10, 조회 실패 시 신호가 폴백 —
  trader.log의 "[체결]" 로그로 확인 가능). **그 이전 거래(SELL 3건 포함)는
  주문 시점 현재가**라 슬리피지 미반영 — 실측 손익 집계 시 혼합 주의.
  일일점검 시 당일 매매가 있었다면 "[체결]" 로그에서 폴백 발생 여부 확인.

### 6. 신규 기능 가동 확인 (2026-07-03 배포분)
- **휴장일 체크 판정**: 영업일인데 trader.log에 "휴장일" 문구가 있으면
  **오판(즉시 보고)**. 휴장일인데 "예수금:" 스캔 로그가 이어지면 미작동.
  정상 = 영업일엔 아무 흔적 없음, 휴장일엔 "휴장일(개장일 아님)" 1회 후 침묵.
- **[체결] 로그**: 당일 매매가 있었다면 [매수]/[매도] 직후 "[체결] ...
  체결가 ...원 (신호가 ...원)" 확인. "폴백" 문구면 체결 조회 실패 —
  1회성이면 기록만, 반복이면 kis-code-change 이관. trades.db price와
  [체결] 로그 체결가 일치 확인.
- **[관찰] 배치**: 08:30 "아침 시장 스캔 완료" / 16:00 "저녁 시장 스캔 완료"
  + market_scan_cache.json의 scanned_at. 실패해도 매매 영향 없음(관찰 전용) —
  원인 기록만.
- **그리드서치 주기**: model_version.trained_at이 7일 초과면 "수동 실행 필요"
  안내만 (--check는 스케줄러 미등록 — 직접 실행하지 말 것, 648조합 약 2.4분).

### 7. trades.db 백업·무결성
- `PRAGMA integrity_check` 결과 ok 확인 (이상 시 즉시 보고).
- SELL 누적 건수가 전일 점검 대비 **감소**했다면 데이터 손실 신호 — 즉시 보고.
- 실측 30건이 유일한 검증 자산 — 주 1회 `trades.db` 사본 백업 권고
  (예: `Copy-Item trades.db trades_backup_YYYYMMDD.db`). 백업 파일은 gitignore 대상.

### 8. 텔레그램 발송 상태
- trader.log에서 notifier 관련 오류 패턴 확인. notifier는 토큰 미설정 시
  print 폴백이므로 "로그에 오류 없음 + 미수신"이면 토큰/네트워크 문제.
- 08:50 premarket_check 미수신의 원인 분리(스케줄러/스크립트/notifier)는
  **kis-ops-infra** 관할 — 증상만 확인하고 이관.

### 9. 스케줄 실행 여부
- 08:00 `start_trader.ps1`이 Windows 작업 스케줄러로 정상 실행됐는지
  (중복 실행 방지 로직이 있으므로 수동 실행과 충돌은 없음).
- 08:50 `premarket_check.py` 텔레그램 알림이 왔는지 — 단, 이 스크립트는
  **trader.log에 기록을 남기지 않으므로** 로그로는 검증 불가. 텔레그램
  수신 여부를 사용자에게 확인 요청하는 것으로 처리한다.
- 08:30 `_run_morning_recheck()`이 watchlist 갱신 → 신호 재스캔 →
  아침 재검증 순서로 실행됐는지 로그에서 순서를 확인한다(순서가
  깨지면 안 됨, CLAUDE.md 명시).
- 17:00 `stop_trader.ps1` 정상 종료 여부는 trader.log **마지막 줄의
  시각**으로 판정 — 16:59:5x면 정상 종료, 17:00 이후로도 로그가
  이어지면 종료 실패(스케줄러 또는 WMI 필터 문제).

## 이상 발견 시 처리 원칙

- 이 스킬은 진단만 한다. 코드 수정이 필요하면 "kis-code-change
  스킬로 넘겨서 수정할 것을 권장"한다고만 안내하고, 직접 코드를
  고치지 않는다.
- 일시적 이상(예: 하루 매매 0건)과 구조적 이상(예: 캐시 파일이
  3일째 갱신 안 됨)을 구분해서 보고한다 — 전자는 정상 범위일 수
  있다고 명시한다.
- 실측 SELL 건수가 30건에 가까워지면, kis-backtest-result 스킬로
  넘어가 백테스트 대비 실측 비교를 시작하라고 안내한다.

## 출력 형식

```
[점검일시] YYYY-MM-DD HH:MM
[토큰 상태] 정상/이상 — 근거
[로그 이상] 없음/항목 나열
[일일손실한도] 정상/발동 중 — 발동 시 실현손실액
[캐시 상태] news_dart / watchlist / name / premarket / market_scan 각각 최종 갱신 시각
[오늘 매매] BUY n건 / SELL n건 — 정상 범위 여부 + [체결] 로그 확인 결과
[누적 SELL] n건 / 30건 (LOCKED 해제까지 남은 건수)
[신규 기능] 휴장일 체크 / 체결가 기록 / 관찰 배치 — 정상·이월·이슈
[DB 무결성] integrity_check / SELL 건수 증감
[스케줄 실행] 08:00 / 08:30 / 08:50 / 16:00 / 17:00 각각 정상 여부 (인프라 원인은 kis-ops-infra 이관)
[종합 판정] 정상 운용 중 / 주의 필요 / 즉시 조치 필요
[조치 필요 시] kis-code-change로 넘길 항목 목록
```
