# 골프 실시간 분석 — 설계 지침

## 핵심 제약: 현재 감지 알고리즘은 post-hoc 구조

`SwingPhaseDetector.detect_all_phases()`(analyzer/phase_detector.py L.47-147, 2026-07-04
모듈 분리로 app_v2.py에서 이동됨)는 **전체 `wrist_y_history` 시계열을 다 모은 뒤에** 실행된다:

- `addr_end`(어드레스 끝)는 전체 y_range(`wy.max() - wy.min()`, L.66)를 알아야 계산 가능
- `top_idx`(백스윙 톱) 폴백은 `addr_end` 이후 70% 구간에서 argmin — 이 구간 자체가 전체 길이(`n`) 기준
- `impact_idx`는 `top_idx` 이후 70% 구간의 argmax — 역시 전체 길이 필요
- `follow_idx`는 `impact_idx` 이후 남은 구간의 argmin

즉 스윙이 끝나기 전에는 어떤 경계도 확정할 수 없다. **이 구조를 그대로 실시간에
가져다 쓸 수 없다** — 웹캠 스트림에서는 "지금이 임팩트인지"를 스윙이 끝나기 전에
판단해야 하는 경우가 많다(예: 임팩트 순간 HUD 하이라이트).

## 설계 방향 — 두 갈래로 분리해서 접근

### 방향 A: 스트리밍 중엔 원시 지표만, 페이즈 확정은 스윙 종료 후
- 실시간 중에는 스켈레톤 오버레이 + 관절각(척추각/회전각/무릎/팔꿈치, analyzer/geometry.py 함수 그대로 재사용 가능)만 매 프레임 표시
- 스윙 종료를 감지(예: 손목 Y가 일정 시간 안정 = 피니시 정지)한 시점에 버퍼링된 시계열로 기존 `detect_all_phases()`를 그대로 호출 — **분석 코어는 재작성하지 않는다**, "코어 보존" 원칙과 일치
- 장점: 검증된 알고리즘 재사용, 회귀 위험 최소화 / 단점: 임팩트 순간 실시간 하이라이트 불가

### 방향 B: 슬라이딩 윈도우 기반 증분 감지 (신규 알고리즘 필요)
- 최근 N초 버퍼만 유지하며 실시간으로 어드레스/백스윙/임팩트 후보를 갱신
- `top_idx`의 속도 부호 전환 감지(analyzer/phase_detector.py L.86 부근, "직전 음수·직후 양수" 패턴)는 슬라이딩 윈도우에도 적용 가능 — 이 부분은 이미 국소적(local) 판단이라 실시간 전환이 상대적으로 쉬움
- 반면 `impact_idx`(argmax) 방식은 "이후 70% 구간"이라는 전역 기준이 필요해 실시간에는 "톱 감지 후 일정 시간 내 최댓값" 같은 근사로 바꿔야 함 — **이건 새 알고리즘이며, golf-analysis-quality로 회귀 검증 필수**
- 장점: 실시간 하이라이트 가능 / 단점: 정확도 트레이드오프, 새로 검증 필요

어느 방향을 택할지는 사용자에게 실시간의 용도(운동 중 즉각 피드백이 필요한지,
스윙 후 리뷰면 충분한지)를 확인하고 결정한다. 기본 추천은 방향 A — 코어 보존
원칙에 부합하고 구현 리스크가 낮다.

**현황 (2026-07-05, golf-platform 5단계)**: 방향 A로 `web/`에 구현 완료 —
`web/src/components/LiveCapture.tsx`(온디바이스 `@mediapipe/tasks-vision` +
`geometry.ts` 포팅), 스윙 종료는 자동 감지가 아니라 사용자 버튼 방식, 종료 시
손목Y 시계열만 기존 `/detect-phases`로 전송(서버 무변경). 상세는 CLAUDE.md
"Live webcam analysis" 섹션.

**2026-07-10 확장 (P3)**: 라이브 세션에 점수·이슈·AI 코칭 연결 완료 — 여전히 방향 A.
`LiveCapture.tsx`가 가시성 게이트를 통과한 프레임의 각도 7종(geometry.ts)을 wrist_y와
1:1로 버퍼링해 종료 시 신규 `POST /score-live`(server/main.py)로 전송하고, 서버는
`detect_all_phases()`→`get_phase_for_frame()`→`compute_summary()`→`compute_score()`를
그대로 호출한다(코어 무변경). `/detect-phases`는 유지되나 라이브 흐름은 더 이상 쓰지 않음.
**잔여 범위**: 모바일(Capacitor) 앱 통합 미착수, 방향 B(실시간 임팩트 하이라이트)는
미채택 상태 — 이 스킬은 이제 이 확장들을 다룰 때 적용된다.

## 온디바이스 vs 서버 처리 트레이드오프 (PPTX 슬라이드 10 비전)

PPTX가 명시한 목표: "무거운 서버 인프라 없이 스마트폰·브라우저에서 30fps 이상 연산,
5% 이내 오차율". 이 목표를 실시간 기능에도 적용할지 판단 기준:

| 항목 | 온디바이스 (브라우저 MediaPipe Tasks JS 등) | 서버 처리 (현재 Python MediaPipe 유지) |
|---|---|---|
| 지연시간 | 낮음 (네트워크 왕복 없음) | 프레임 전송·응답 지연 발생 |
| 정확도 | MediaPipe 모델 자체는 동일 계열, JS 포팅 시 재검증 필요 | 현재 검증된 Python 파이프라인 그대로 사용 |
| 개발 비용 | 각도 계산·페이즈 감지 로직을 JS로 포팅 필요 (analyzer/geometry.py, analyzer/phase_detector.py 재구현) | 기존 코드 재사용, 스트리밍 인프라만 추가 |
| 모바일 앱 적합성 | 네이티브 성능에 가까움 | 네트워크 의존 |

`analyzer/geometry.py`, `analyzer/phase_detector.py` 로직(정규화, 각도 계산, 페이즈 감지)을
JS로 포팅하는 경우, **원본 Python 구현과 동일한 결과를 내는지 반드시 회귀 검증** —
코사인 제2법칙(geometry.py L.27-32), 어깨폭 정규화(geometry.py L.4-22) 등 수식이 정확히 일치해야 한다.

이 트레이드오프 자체가 되돌리기 어려운 구조 결정이면 golf-platform 판정을 먼저 받는다.

## 30fps 예산 체크

- 현재 `process_video()`는 영상 업로드 후 배치 처리라 실시간 프레임 예산 제약이 없음
- 실시간 전환 시 프레임당 처리 시간 예산 ≈ 33ms(30fps 기준) — MediaPipe 추론 + CLAHE 전처리(analyzer/pipeline.py L.259-261) + 각도 계산을 이 안에 맞춰야 함
- CLAHE는 현재 배치 처리에서도 프레임마다 실행되는 무거운 연산(analyzer/pipeline.py L.231, 259-261) — 실시간에서 유지할지, 조명 조건이 양호하면 생략할지 결정 필요
